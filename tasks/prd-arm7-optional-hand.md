# PRD：G1 独立手臂控制与可选灵巧手支持

日期：2026-10-16。状态：用户已确认并要求实施；技术契约见 [SPEC](spec-arm7-optional-hand.md)。

## 1. 背景

当前设备可接收身体状态，但未收到双手 Dex3 状态，手部适配原因尚未定位。现有 28 关节耦合使手臂流程也被阻塞。近期先支持独立双臂，保留 Dex3 实现，通过显式配置选择是否控制手部及支持的型号。

## 2. 目标

- 无任何手部反馈时，14 关节 Arm7 仍可示教、制作动作、规划过渡和回放。
- 明确选择 Dex3-1 时保留 28 关节能力，缺帧必须失败，不自动降级。
- 控制布局与实体手几何分开，未控制手部仍考虑实体手完整活动范围。
- 保留现有 Dex3 文件读取，不自动截断或补零。
- 共用示教和回放流程，不实现未知硬件的通用插件框架。

## 3. 用户故事

### US-001：通过配置选择控制布局

作为操作人员，我希望沿用 --profile 选择仅手臂或带 Dex3-1 控制。

- [ ] 支持 unitree-g1-arm7 和 unitree-g1-arm7-dex3-1。
- [ ] 仅手臂无需手部增益；Dex3 要求完整手部参数。
- [ ] 未知型号、缺失必填字段明确拒绝，不自动探测或降级。
- [ ] 参数检查不初始化 DDS、不发送控制命令。

### US-002：没有手部反馈时使用手臂状态

作为操作人员，我希望仅手臂模式不被手部断流阻塞。

- [ ] 身体消息形成14关节快照；仅手臂不创建任何手部通道。
- [ ] 仅手臂不要求 SDK 提供手部类型或消息工厂。
- [ ] 身体无效或过期必须失败；Dex3 任一手部无效或过期仍必须失败。

### US-003：完成仅手臂示教

作为操作人员，我希望沿用完整示教交互，只对选中手臂应用示教增益。

- [ ] 保留接管、软化、两次回车录制、终点保持、恢复、避碰回位、稳定及释放。
- [ ] 左右侧各7个受控手臂关节，另一侧保持基线。
- [ ] 保存14关节 q／dq 和明确的布局及顺序，全程不发送手部命令。
- [ ] 取消、输入关闭、失效反馈和规划失败保留清理与现场接管语义。

### US-004：制作和读取动作

作为动作制作者，我希望文件明确表示布局并避免错用。

- [ ] 14关节录制可制作统一动作；旧 Dex3 文件仍可读取。
- [ ] schema 表达结构版本，target_profile 和 joint_names 表达布局。
- [ ] 数量或顺序不一致、非有限值、摘要损坏等输入被拒绝。
- [ ] 不改写原文件，不截断、不补零；保留时间轴及首末实测姿态。

### US-005：规划和回放仅手臂动作

作为操作人员，我希望仅手臂动作支持预览、拼接、进入和回位。

- [ ] 单动作和多动作均支持速度调整、另一侧保持、过渡及回位规划。
- [ ] 混用动作布局或动作与 profile 不匹配时，在创建控制发布器前拒绝。
- [ ] 默认预览不连接设备，仅 --execute 进入控制路径。
- [ ] 报告记录布局、控制数量、手部是否启用，不声称未启用手部已释放。

### US-006：未知手型下保留实体手避碰

作为操作人员，我希望只控制手臂仍考虑实际安装的手。

- [ ] 本期支持 Dex3-1 实体几何，其他型号明确拒绝。
- [ ] 没有手指反馈时覆盖完整模型活动范围，保留掌部与帧间检查。
- [ ] 检查躯干、同侧非安装区、对侧手臂和另一只手，不能整体排除同侧手臂。
- [ ] 覆盖依据为几何上界，随机姿态只作辅助；不能证明则拒绝。
- [ ] 报告区分完整活动包络与实测关节姿态检查。

### US-007：配置与迁移文档

作为维护者，我希望从文档独立选择模式并理解旧文件如何继续使用。

- [ ] 提供两类完整配置示例及对应命令。
- [ ] 说明旧格式读取、新格式输出和布局不匹配拒绝。
- [ ] 更新 CLI 与交接记录，明确未控制手部不等于卸力。
- [ ] 不将离线或模拟 SDK 通过表述为真机资格确认。

### US-008：完整用户路径自动化验收

作为维护者，我希望连续验证命令入口到文件、规划及执行报告。

- [ ] 模拟示教 → build → transition → 预览 → 模拟执行，使用上一步真实输出。
- [ ] 仅替换 SDK、时钟和人工输入，采用真实 MuJoCo／OMPL 规划。
- [ ] 零手部反馈及能力，完整流程仍通过，并断言零手部通道和命令。
- [ ] 覆盖布局不匹配、身体断流等关键失败路径；验证输出布局和摘要。
- [ ] Linux CI 中必须运行，依赖缺失或跳过不算通过；独立测试数据，不连真实 DDS。

## 4. 功能需求

- FR-1：系统必须通过 profile 的 target_profile 选择控制布局。
- FR-2：系统必须将实际手部碰撞型号与控制布局分开表达。
- FR-3：系统必须拒绝未支持的控制布局或实体手型号。
- FR-4：系统必须按布局校验所需增益参数。
- FR-5：系统必须按布局形成完整状态快照。
- FR-6：系统必须在仅手臂模式禁用所有手部 DDS 通道。
- FR-7：系统必须在 Dex3 模式保留双手反馈有效性检查。
- FR-8：系统必须共用完整示教业务流程。
- FR-9：系统必须在文件中明确记录控制布局。
- FR-10：系统必须继续读取现有 Dex3 录制和动作文件。
- FR-11：系统必须拒绝不同布局的动作组合。
- FR-12：系统必须拒绝动作与执行 profile 的布局不匹配。
- FR-13：系统必须使用明确实体手模型处理仅手臂避碰。
- FR-14：系统必须将手部包络纳入完整轨迹和帧间检查。
- FR-15：系统必须在无法证明几何检查通过时停止规划。
- FR-16：系统必须区分手部控制未启用和手部释放情况。
- FR-17：系统必须保留显式 --execute 控制边界。
- FR-18：系统必须保留输出文件不覆盖行为。

## 5. 非目标

不修复现场手部供电、接线或服务；不新增其他型号驱动、自动识别、自动降级、动作布局转换、动态插件系统；不改变超时、接管或固件保护策略；不执行真机动作或自动确认控制权交接。

## 6. 技术与设计约束

使用 Python 3.11、标准库布局对象、现有 unittest 和 SDK 注入；不增加默认运行依赖。关节数从名称推导，布局只进入有语义的边界，纯数学函数保持通用。旧文件仅在加载入口归一化。

保留手部实体碰撞几何。用户选择完整活动包络，不以零位手指或固定手型代替未知反馈；规划继续在发送控制前或工作线程中进行。

## 7. 成功标准与待验证事项

仅手臂完整模拟路径在零手部能力下通过，Dex3 回归通过，错误布局在控制发布前失败，包络及帧间检查通过，相关 lint 和 Linux 测试通过。测试跳过不能视为验收。

内置模型是否适合实际硬件仍需现场核实；球包络的保守程度必须经过真实几何可用性门槛。2026-10-16 用户已授权首版球失败后改用更细但仍覆盖完整范围的包络，最终算法由 SPEC 与手部包络说明定义。
