# 2026-10-16 真机示教失衡：历史部署取证

本文归档 2026-10-16 项目重写前的部署事故与当时的离线审计。下述代码问题、命令、测试数量和程序行为均属于第 1 节锁定的冻结版本，不代表当前实现；旧命令仅为现场证据，不能作为现行操作步骤。当前使用方式见 [项目 README](../README.md)。

原审计仅检查本机文件、冻结部署包和宇树公开资料，并运行内存中的离线复现，没有再次连接机器人或初始化 DDS。本次文档整理未重新执行这些审计，也未新增真机验证。

## 结论

冻结版本已经确认一个与整机稳定性直接相关的接口实现错误：**发送器只填写双臂的 15–28 槽位，却将 `rt/arm_sdk` 的整体控制权重升到 1；同一报文中有效的腰部 12–14 槽位一直保持 SDK 默认的全零指令。**

原审计查阅的官方接口将 12–28 定义为腰部与上肢控制参数，并非只有 15–28 有效。现场读到的 FSM 是 501，官方定义为三自由度腰部常规运控；冻结代码还把 501 写成了允许接管的硬性条件。因而“只给双臂字段赋值，腰部就会保持原控制”的假设没有成立依据。这是该次审计最有证据支持的失衡触发候选，不能用“增益参数未验收”概括。

同时，控制循环在等待录制前已经完成实际接管，却没有腿腰漂移、IMU 或速度保护；随后右臂跟踪误差触发停发，程序没有发送权重归零。这些是已复现的监测和退出缺陷。

**尚不能把“腰部最终被接收端以哪种方式处理，如何开始整机晃动”写成已经观测到的唯一物理根因。** 原审计未取得事故每周期报文、接收端运控日志、IMU 轨迹和固件实现。以下分别标注发送端事实、现场终端证据、离线注入结果与因果推断。

## 3. 冻结程序的发送逻辑

调用链为 `cli → teach() → run_session() → tick() → ReplaySdkPort.write() → publisher.Write()`。

旧 `src/replay_sdk.py` 的 `ReplaySdkPort.write()` 每轮新建 `LowCmd`，只遍历 `ARM_SLOTS=15..28`，设置 29.q，计算 CRC 后发送整个消息，不存在“未赋值的腰部槽位不随报文发送”的机制。

| 槽位 | 报文内容 | 说明 |
| --- | --- | --- |
| 0–11 | mode/q/dq/tau/kp/kd 全零 | 腿部；官方 `rt/arm_sdk` 有效索引表不包含这些槽位，不能因此声称直接命令腿部归零 |
| **12–14** | **mode=0、q=dq=tau=kp=kd=0** | **官方定义的有效腰部控制字段，被遗漏** |
| 15–21 | mode=1；q 为左臂目标；dq=tau=0 | 左臂，保持阶段 kp/kd=60/1.5，示教阶段 20/1.5 |
| 22–28 | mode=1；q 一直保持接管前右臂基线；dq=tau=0；kp/kd=60/1.5 | `--side left` 仍主动保持右臂，不是只给左臂发送命令 |
| 29 | q 是控制权重 | 2 秒内 0→1；等待开始时已经是 1 |
| 30–34 | 默认零 | 官方该接口有效索引表不包含这些槽位 |

消息头使用 `mode_pr=0`，`mode_machine` 从反馈取值，现场为 5。Arm7 布局不创建 Dex3 指令发布器，不给手指发送弯曲角度。固定手型和忽略手部碰撞只影响几何检查，不会自动建立任何腰部保持指令。

现场已经出现“摆好起点后按回车开始录制”提示。依照旧 `src/teach.py` 的会话顺序，能推出此前已经经过：

1. 初始几何检查通过；启动 `rt/arm_sdk` 发布器。
2. 2 秒内权重 0→1，双臂保持基线，增益 60/1.5。
3. 接下来的 2 秒权重保持 1，左臂改为追随反馈，左臂 kp 从 60 降到 20，kd 保持 1.5；右臂仍保持基线和 60/1.5。
4. 等待回车期间继续按第 3 项发送，而不是只读等待。未观察到 `RECORDING_STARTED`，没有执行动作序列回放。

以上是由冻结源代码和现场提示推导的阶段，不是恢复出的每个真实网络数据包；实际发送数量、精确每周期时刻和事故时 q 值没有留存。

## 4. 冻结代码问题与原审计复现

### P0：遗漏有效腰部字段，却接管整个上肢接口

冻结源码：`src/constants.py` 的关节布局、`src/replay_sdk.py` 的报文填充与 FSM 检查。

14 个动作关节的布局被直接用作整个 SDK 报文的填充范围。动作只记录双臂是合理的，但这不等于 SDK 的有效控制范围也只有双臂。每次新建报文都把三个腰部参数恢复为零，又要求现场 FSM 必须是 501，随后使 SDK 权重达到 1。

默认零不是“保持当前腰部”的表达。若高层接收端采用这些槽位的增益/力矩，则 kp=kd=tau=0 无法表达腰部保持；若透传 mode，0 又具有 Disable 含义。**具体哪种处理发生在这台机器人上，需要接收端证据，不能自行选一种当成已观测事实。** 官方例程未显式设置 mode 也能用于高层控制，反而说明不能想当然地把 mode=0 当成高层接口的“忽略此关节”标志。

这解释了为什么一个名为“手臂示教”的程序可能影响躯干：它使用的是带腰部控制字段的上肢混合接口，不是左臂独立通道。

离线验证：从冻结 `write()` 原文提取 AST，使用官方真实 LowCmd 工厂、IDL 和 CRC，发送到只保存内存的替身。权重 0、0.5、1，以及左臂示教增益 20 的四种消息，腰部字段始终全零；四条均完成 1004 字节 XCDR 和 CRC 往返检查。SDK 通道模块未导入，socket 被禁止。

### P0：异常停发没有完成控制交回

冻结源码：`src/teach.py` 的异常退出路径、`src/replay_sdk.py` 的通道关闭。

正常路径最后才执行 `ramp(2, 1, 0)`。发生跟踪误差后跳到 `finally`，这里只设置 stop 并关闭通道，既不降权重，也不向接收端确认交回。

现场终端显示：

```text
失败：示教在等待开始阶段停止：示教保持或回位跟踪误差超限；未自动释放，请现场接管
```

此时最后发送阶段的权重为 1。关闭发布器不会追补一条 29.q=0 的消息。接收端失去命令后是保持、超时、切回还是采取其他行为，现有证据不能确定；**不能把本程序 `STATE_TIMEOUT=1` 当成机器人控制端的一秒释放保护**，它仅是本程序检查反馈接收时间的阈值。

离线注入右臂偏差 0.16 rad 后，冻结代码复现相同阶段、相同错误；最后权重 1，首次正权重之后没有任何归零消息，所有本端通道已关闭。这证实“关闭资源”和“释放控制”在该冻结实现中是两件事。

### P1：等待开始阶段的报错来自右臂，左臂误差保护被跟随逻辑消掉

冻结源码：`src/teach.py` 的跟随目标更新与误差比较。

```python
if follow:
    target = list(baseline)
    for i in selected:
        target[i] = state["q"][i]
if max(abs(a - b) for a, b in zip(state["q"], target)) > 0.15:
    raise RuntimeError("示教保持或回位跟踪误差超限")
```

现场是 Arm7 `--side left`。在该阶段，左臂 7 个 target 在比较前刚被赋成同一快照的左臂 q，因此七项误差都为零。右臂保持基线，只有右臂偏差能够触发本条错误。**可以确定出错侧为右臂；无法确定具体哪个右臂关节，因为代码没有记录。**

因此，错误不是“人拖动左臂超过 0.15 rad，所以正常停止”。左臂在本循环中甚至可以在相邻两次反馈间跳动 0.3 rad，target 会同步跳动，并通过这个误差判断。离线注入已复现这一点。此处也没有发送目标的独立速度/加速度限制。

### P1：整机监测在最需要的时候没有启用

冻结源码：`src/teach.py` 的 `planned_body` 条件与 `tick()`、`src/replay_sdk.py` 的反馈回调。

`planned_body` 从 None 开始，直到录制结束、恢复刚度之后才赋值。腿/腰偏移超过 0.02 rad 的检查以 `planned_body is not None` 为前提，所以在接管、降低刚度、等待回车和录制期间完全不运行。初始时读到 body_q 和通过一次碰撞检查，并没有激活运行时腿腰监测。

`_on_state()` 不保留 IMU；`tick()` 只验证 dq 数值有限，不检查实际速度上限；服务 FSM 只在接管前查询一次。`mode_machine=5` 是机型，并不证明 FSM 持续为 501 或机器人仍保持平衡。

离线向等待循环注入腰部偏差 0.1 rad，仍继续发送；注入左臂 dq=20 rad/s，也继续发送。两项复现均最后由审计脚本主动注入 EOF 结束，不能把该结束误说成已有保护成功触发。

### P1：示教侧实际是“位置目标追随反馈，前馈为零”，不具备本地重力补偿

冻结源码：`src/teach.py` 的跟随目标、`src/replay_sdk.py` 的 q/dq/tau 字段。

左臂每轮设置 q_target=q_feedback，dq_target=0、tau_ff=0。按 PD 控制的通常含义，采样时位置恢复项被归零，速度项仍会产生阻尼；这不是单纯把一个固定位置保持器从 kp=60 调到 kp=20。该实现没有计算示教侧重力前馈，也没有记录 tau_est 以判断实际承载。

因此左臂能否在被托住、拖动和松手时保持可控，不能由“kp 只有 20”推出。右臂则相反，始终用基线目标和较高刚度保持。该不对称控制会改变上半身受力，但其对这次整机晃动的定量贡献无法由原审计数据测定；不能声称已经证明由左臂重力造成。

### P2：阻塞输入线程导致异常后的解释器崩溃

冻结源码：`src/teach.py` 的 daemon 输入线程与异常退出路径。

输入线程是 daemon，阻塞在 `input()`；stop Event 不能中断正在等待 stdin 的调用，退出路径也不回收这个线程。现场随后出现：

```text
Fatal Python error: _enter_buffered_busy: could not acquire lock for
<_io.BufferedReader name='<stdin>'> at interpreter shutdown,
possibly due to daemon threads
```

代码结构与该错误相符。这发生在控制循环已报错并进入解释器退出阶段，**没有证据把它认定为之前整机开始晃动的原因**。但它确实使异常后的结束与证据保存更加不可靠。

## 5. 旧测试的覆盖边界

冻结版本的 `tests/fake_sdk.py` 是接口与一阶位置滞后的替身，只把 15–28 的 q 和 29 的权重用于模拟。腰部控制参数没有进入该模型，`body_q` 默认固定，增益也不参与真实力矩动力学。它既不会因漏写腰部而失去支撑，也不会模拟失衡。

旧交互测试还用能立即执行目标的内存端口，并替换输入线程，无法暴露 stdin 的 daemon 关闭问题。旧异常测试会断言最后仍有正权重，但这种断言只证明“不乱发新的恢复指令”，不能证明“机器人已安全交回”。

146 项 Linux 测试的日志是 `data/hand-excluded-full-linux.log`，仅证明这些离线逻辑测试通过。真实 IDL/CRC 的离线审计也只证明消息格式一致，**没有验证报文语义是否覆盖完整上肢控制范围**。原审计发现的全零腰部报文，同样能通过 CRC。

**203/207 是离线复现的写入数量，不是事故实测数量。** 输入状态、故障量和报文 q 是明确的合成数据。会话复现使用本机 Python 3.11 和冻结的完整控制循环，替换时钟、SDK、初始几何检查与键盘事件；报文复现使用已有 WSL Python 3.10/CycloneDDS 0.10.2，执行冻结 `write()`/`finite_vector()` 的原文 AST 和真实 SDK 消息类，没有改写控制函数，也没有运行完整真机入口。

原审计缺失的关键证据包括：现场每周期完整 LowCmd/LowState、IMU、tau_est、接收端是否采用 12–14 的记录、SDK/固件版本及带时刻的操作员观察。旧的 `initial-pose-20261016-111359.json` 是较早姿态，不能当作事故时的初始 q；远端控制台日志也仅有会话终端摘录。本次整理未补齐这些证据。

## 7. 对“为什么整机乱晃”的判断

原审计最有支持的解释是：**上肢接口接管时漏写腰部有效参数，使三自由度腰部没有收到本程序明确的保持指令；随后在缺乏整机监测的情况下继续发送，右臂保持偏差增大到触发停发；停发时权重仍为 1，没有完成控制交回。** 其中“报文漏腰”“监测未启用”“右臂触发”“未归零”已由冻结源码和原审计离线复现证实；“接收端因此改变腰部力矩并开始失衡”仍是主要因果候选，缺少接收端记录才能最终闭合。

不能排除机体先失稳导致右臂误差增大的时序；不能把右臂跟踪错误当成已经查到的初始触发源，也不能说异常停发造成了之前已经开始的晃动。现场没有完成两个动作录制，更没有执行序列回放。

事故前以“手臂槽位没有越界、几何检查通过、离线测试通过”作为继续实际接管的依据，漏掉了官方上肢接口还包含腰部这一关键契约，也漏掉了异常后没有控制交回的缺陷。这是该冻结版本的控制实现和审查错误。本文保留其证据与未确认事项，不评估当前实现的修复完成度或硬件验收状态。
